## Objective and validator recheck

The builder's two-stage integer DP remains sound. Stage one enumerates every
nonempty predecessor segment and minimizes the maximum segment sum. With that
cap frozen, future cost depends only on fragment count and end position, so
stage two can retain the minimum pair of exact scaled deviation and cut tuple.
The scaled value
`sum(abs(F * fragment_bytes - total_bytes))` is exactly `F` times total
absolute deviation from the average, and tuple ordering supplies the required
earlier-cut tie break without floating-point selection.

The corrected validator now performs two distinct comparisons:

1. `actual_cuts` is derived from every actual fragment end except the final
   endpoint. Actual maximum and scaled deviation are derived from validated
   actual fragment byte sums. The stored `FragmentObjective` must equal this
   exact actual tuple.
2. `partition_layer_bytes()` independently recomputes the optimum from the
   registry-bound ordered layer bytes. The actual tuple must equal that
   optimum, including cuts, not only maximum size.

This closes all three ways the old representation could decouple:

- non-optimal actual cuts plus an optimal decoy objective fail comparison 1;
- a truthful objective for non-optimal actual cuts passes comparison 1 but
  fails comparison 2;
- an optimal maximum/deviation with a later tied cut fails comparison 2
  because the optimal cut tuple includes the tertiary rule.

The prior independent examples still agree:

- `(1,5,1,4), F=3`: cuts `(1,2)` give `(1,5,5)`, maximum `5`; alternative
  actual cuts `(1,3)` give `(1,6,4)`, maximum `6` and are rejected.
- `(0,0,1,1,2), F=3`: minimax cap `2`; cuts `(3,4)` have scaled deviation `4`
  versus `8` for cuts `(1,4)` or `(2,4)`, proving secondary precedes front
  tie-breaking.
- `(1,1,1,1,1), F=2`: cuts `2` and `3` tie on maximum `3` and deviation `2`,
  so cut `2` wins.
- `(2,2,50,2,2), F=3`: the `50`-byte layer must remain a complete singleton
  to achieve cap `50`.
- The exhaustive count is exactly
  `(6^3-1) + 2(6^4-1) + 3(6^5-1) + 4(6^6-1) = 212750`.

## Synchronization-byte and identity binding

- Registry `sync_dtype_bytes` must now be a positive integer.
- Every registry parameter must have nonnegative `numel` and exact
  `sync_bytes = numel * registry.sync_dtype_bytes`; layer parameter/byte sums
  are then recomputed from those records.
- Map `sync_dtype_bytes` must equal the bound registry field, while map layers
  must exactly equal registry-derived layer summaries. Fragment byte sums are
  recomputed from those layers before the actual objective and balance are
  checked.
- Unsupported fragment-map schema versions are rejected in addition to the
  canonical digest and registry-digest checks.

Therefore changing only map dtype now fails immediately. Changing parameter
bytes and adjusting layer summaries plus the registry digest still fails the
per-parameter multiplication check. Adjusting parameter records consistently
produces a genuinely different registry/map identity rather than disguising
the old one.

## Maker-unlisted counterexamples rechecked

1. Wrong deviation only: retain actual cuts and maximum but alter only stored
   scaled deviation and recompute the digest. Stored-versus-actual objective
   comparison rejects it.
2. Truthful but non-optimal map: change actual cuts, actual objective and
   balance together so they are mutually consistent. Actual-versus-optimal
   comparison rejects it.
3. Tertiary disguise: select a later cut with equal maximum and deviation and
   report it truthfully. The independently optimal tuple contains the earlier
   cut, so equality rejects it.
4. Parameter-byte disguise: modify a parameter's byte count, its layer sum and
   registry digest together while retaining the same dtype. Exact
   `numel*dtype_bytes` validation rejects it before partitioning.
5. Balance-only disguise: actual objective may be correct, but modified
   total/min/max/average/ratio fields are reconstructed and rejected by exact
   `BalanceSummary` equality.

No counterexample above survives the corrected validation path.
